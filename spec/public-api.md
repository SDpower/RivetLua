# 公開 API 契約草案

未來介面包含 `Compiler.compile`、`Compiler.compile_ast`、`Vm.load`、`Vm.call`、`Vm.resume` 與 `ModuleCodec.encode`／`decode`。它們的 module 必須已驗證，不能提供任意 bytecode 建構入口。

公開 bytecode API 提供只能由 decode/verify 建立的 immutable `VerifiedModule`，並可讀取 `format_version()` 與 `profile()`；RVLU_V2 另公開封閉 `InstructionEffects` static contract。這些 API 不執行 Lua。原始草案把 `Returned`、`Yielded`、`LuaError`、`Aborted`、多重回傳與 VM 身分 handle 列為 P06+ 待實作項；其後 P06～P13 的實際進度以各階段驗收紀錄為準。P14 公開 SDK 第 8 步、container／安全 decode 第 9～10 步、VM state separation 第 11 步及第 12a SDK adapter 已由主代理複審接受；第 12b CLI adapter 亦已完成局部驗收並由主代理接受。SDK-001～008／negative controls 已建立雙 profile 可執行案例；完整 fresh gates 與 P14 總驗收仍待最終執行。

2026-10-03 使用者授權新增 Lua 5.5.1／5.4.9 官方 chunk 的純 Rust 匯入／輸出介面。呼叫端必須明確指定 profile 與能力政策；P05 先依版本檢查官方結構、CFG、資源限額，再轉成既有 RVLU_V2 並驗證。`VerifiedModule.origin()` 區分 `OfficialImport` 與 `NativeRvlu`；官方匯入的不可變 artifact 由同一 P05 轉譯路徑建立，保留原始官方 prototype／constant／upvalue／debug 位元組、來源名稱及官方 PC↔RVLU PC 對應。公開執行計畫候選的驗證不能把 `NativeRvlu` 升級為官方來源；裸 RVLU_V2 decode 也不產生官方 artifact。P14 `Module`／container 可保存已驗證 artifact，但不得自行建構它。現有受限 debug capability 可讀官方來源、行號與 guest upvalue 名稱／數量，合成綁定仍不可見；一般 RVLU 的 debug 政策不因 artifact 支援而放寬。load／dump 不保存 closure capture、執行堆疊、coroutine、root 或宿主資源；官方 chunk、RVLU_V2、Lua 語意與 C ABI 是不同契約。P05 匯入 metadata 與 P13 capability-controlled load/dump 已有局部測試；P14 第 8～11 步及第 12a adapter 已由主代理複審接受，第 12b CLI 局部驗收已由主代理接受；SDK-001～008／negative controls 已建立雙 profile 可執行案例，完整 fresh gates 與 P14 總驗收仍待最終執行。

P05 公開 `encode_transport_module(&VerifiedModule, &TransportLimits, &mut OfficialWorkBudget)` 與 `decode_transport_module(rvlu_bytes, sidecar_bytes, expected_profile, &TransportLimits, &mut OfficialWorkBudget)`。編碼結果 `EncodedTransportModule` 只能讀取或消費為 RVLU／sidecar 兩段 bytes，不能任意建構可信 metadata。P14 可以在配置前先呼叫 `transport_encode_scan_admission` 或 `transport_scan_admission` 預扣掃描量，再呼叫 `preflight_transport_encode`／`preflight_transport_decode` 預扣衍生的工作、temporary 與 retained 上界；輸入在兩階段與操作期間必須不變。`TransportErrorKind` 區分格式、限額、配置、RVLU、官方來源及轉譯錯誤。P05 在讀取 sidecar 後重建／重驗私有 metadata，並核對官方來源的完整 canonical RVLU 位元組身份；P14 不解析 RVLU opcode、sidecar 內部欄位或官方 Lua 指令，也不直接序列化 VM 執行狀態。容器與公開 wrapper 由 P14 第 9～10 步負責；本段僅界定 P05 producer API。

第 12 步前置的 compiler producer 公開 `CompileBudgetSink` 與 `compile_with_budget`，沿同一條 lex→parse→resolve→lower→emit/nativeDebug/P05 verify 流程，在各階段工作或配置前向 sink 申報 work、temporary、module allocation；`BudgetedCompileError` 分開保留 Frontend、IR、Bytecode、Budget 與准入溢位／低估。它只回傳已驗證的 `VerifiedModule`，不依賴 runtime。`Vm::load_with_environment_and_args` 接受入口 Lua 參數；既有 `load`／`load_with_environment` 以空參數呼叫，native source root 是無固定參數的 variadic main，非 variadic 巢狀函式的 `...` 規則不變。宿主 source compiler 的 `LoadBudget` 逐階段扣除 fuel 與 ledger，限額／fuel／配置錯誤各保留原本型別；module 的巢狀實際容量由 Core 唯一 helper 核對。

P05 唯一語言輸入分類器 `classify_input` 回傳 `InputFormat::{Source,RawRvlu,Official,UnsupportedBinary}`，只讀固定 header；`RVLU = 1` 與 `RVLU()` 是文字，未知或過短 ESC 簽章仍是 binary 拒絕。bytecode 呼叫端先預付 `input_scan_admission`，再由 `preflight_input_module` 取得後續 work／temporary／retained 上界，預付後消費綁定同一輸入 bytes 的 `InputPreflight` 交給 `decode_input_module`。裸 RVLU 只經 Core 私藏 kind 0 None sidecar 預掃描及一般 decode/verify，不能推測 private plan、NativeDebug 或官方 artifact；官方來源經官方 preflight/decode/translate 保留可信 artifact 與 plan。`InputErrorKind` 區分格式、限額與配置失敗。SDK `Engine::load_binary_module` 依此契約處理 raw／official 輸入與 RVCT 外層；SDK compiler adapter、參數入口與 CLI 為不同層次。

SDK `Engine::compile_named_with_budget` 接同一 `compile_with_budget` pipeline，以可重用 `CompileBudget` 限制單次 work 與 peak allocation；compiler 每段實際容量由 producer 上界核對，SDK 另為回傳 `Module` 的 Arc 預付固定 work 與控制區 charge。`Engine` 可明確以 `LoadCapability::and_compiler(engine.clone())` 啟用 `HostLoadCompiler`；adapter 將 compiler 的每筆 work／temporary／module claim 委派給 runtime 傳入的 `LoadBudget`，保留語法診斷與 budget/fuel/allocation 錯誤。Engine 預設 VM 仍不授予載入能力。`Vm::load_module_with_args` 使用 runtime 的既有入口 frame，檢查 profile、VM identity、物件世代與 root／GC 生命週期；原 `load_module` 委派空參數。SDK 第 12a adapter 已由主代理複審接受；CLI 第 12b adapter 已完成局部驗收並由主代理接受。命令列工具契約與固定 resource／host capability 範圍見 `docs/sdk/cli.md`。

Runtime 的 basic environment installer 依 VM 固定的 Lua profile 建立 `_VERSION` ByteString：Lua 5.4 profile 為 `Lua 5.4`，Lua 5.5 profile 為 `Lua 5.5`。此值是普通 guest 全域欄位，可以替換或刪除；模組與 transport 不保存其執行時狀態。installer 也把 `_G` 初始化為該環境 table 本身；它是普通 guest 欄位，替換或刪除 `_G` 不會改變既有 `_ENV` 綁定。各環境及各 VM 的 `_G` 分別指向自己的 table；這項自參照不額外保根，環境失去可達路徑後仍可由 GC 回收。

同一 basic environment 也提供可由 guest 覆寫或刪除的 `collectgarbage`。Lua 5.4／5.5 的新 VM 均以 Generational GC 模式啟動。目前支援無參數、第一參數為 `nil` 或明示 `"collect"` 的完整回收，以及 `"count"`、`"isrunning"`、`"stop"`、`"restart"`、`"incremental"`、`"generational"` 與 `"step"`；Lua 5.5 額外支援 `"param"`；額外參數沿用 basic 選項的忽略方式。完整回收先完成進行中的增量 cycle，再依現有模式執行 Full 或 Generational Major cycle，回傳單一整數 `0`；即使自動 GC 已停止，明確回收仍執行且不改變自動 running 狀態。`"count"` 回傳一個浮點數，為呼叫當下 VM 帳本的 `lua_heap_bytes / 1024`（KiB，可含小數）；不計入宿主配置、共享 RSS 或僅保留的額度。`"isrunning"` 回傳 VM 自動 GC 是否運作的布林值；這兩個查詢本身不推進 GC 或改變模式、debt 與 root。`"stop"` 暫停自動配置觸發的 GC，`"restart"` 恢復自動 GC 並將自動 debt 歸零，兩者各回傳整數 `0`；明確的宿主 collect／step／minor／major 及 Lua `"step"` 不受 stop 阻止。`"step"` 的可選 size 接受整數或整數數值字串；Lua 5.4 以 KiB、Lua 5.5 以 byte 計量，省略、`nil` 或非正值使用基本步幅，完成 Full／Major cycle 回傳 `true`，未完成或完成 Minor cycle 回傳 `false`，且不改變自動 running 狀態。兩個模式選項各回傳切換前模式的 VM ByteString；不同模式時先完成進行中的 cycle，再沿用既有模式切換規則；相同模式不主動完成或重啟 cycle，但建立回傳字串的配置仍遵循一般自動 GC 規則。模式操作不改變自動 running 狀態。Lua 5.5 的 `"param"` 可查詢或設定 VM 私有的 `pause` 與 `stepmul`，回傳設定前經 Lua 官方壓縮編碼解碼的整數值；省略值、`nil` 或負值僅查詢。`stepmul` 影響增量模式的顯式與自動工作量，`pause` 影響增量 cycle 完成後的自動觸發門檻；宿主明示的 debt threshold 設定優先。Lua 5.4 不支援 `"param"`。finalizer 執行中，無參數、`nil`、`"collect"`、三個 running 控制、兩個模式選項與 `"step"`／Lua 5.5 `"param"` 各回傳單一 `nil`，不變更 running 或模式狀態，也不啟動 GC。其他選項與無效參數回 `E_BASIC_ARGUMENT`；尚未支援的 GC 控制仍標記為 `NOT_IMPLEMENTED`。

P14 SDK 公開 `Engine::save_module(&Module, &TransportBudget) -> Result<Vec<u8>, ContainerError>` 與 `Engine::load_module(&[u8], &TransportBudget) -> Result<Module, ContainerError>`。外層 RVCT v1 使用固定 40-byte header：magic、version、flags、total/RVLU/sidecar 長度、CRC32 與 reserved 欄位；body 只包含 P05 傳回的 RVLU 和 sidecar bytes。CRC32 依 RFC 1952 §8，涵蓋 header CRC 欄位以外的 bytes，僅驗傳輸完整性。load 先完成自身欄位、長度、policy 與完整性檢查，再以無配置 P05 scan／preflight 計算 operation limits，建立 RAII allocation escrow，最後由 P05 重建 `VerifiedModule`。`ContainerLimits` 限制容器 bytes、單次 peak allocation、work 與 P05 `TransportLimits`；`TransportBudget` 重用呼叫端建立的 allocation ledger，但 work、reservation 每次操作新建。外層格式或 checksum 錯誤在 ledger reservation 前回報；payload 錯誤由 P05 結構化拒絕並釋放 escrow，不回傳半成品。此 API 不提供任意 `Module`／`VerifiedModule` 建構，也不保存 VM state。細節與可執行範例見 `docs/sdk/transport.md`。

`Module::clone` 只複製共享 immutable `Arc<VerifiedModule>`；同一 Module、clone 或 RVCT 還原 Module 載入不同 VM 時，各 VM 的 globals、Heap、package loaded/preload registry、coroutine、callback registry、HostServices 與 allocation state 獨立。宿主 handle／`Root` 必須由建立它的 VM 使用，其他 VM 的物件值、ByteString、callback 或 coroutine 會以 VM 身分錯誤拒絕。容器只可重建 module 語意，不保存執行後的 global、closure capture、yield/resume state 或 host resource；重新載入到新 VM 從初始 globals 與新執行狀態開始。宿主明確共用外部 provider 時，其宿主自有狀態可以共享；`Module` 本身不攜帶或傳播 host service 授權或 execution state。

P13 對宿主提供 `Vm::call(Value, &[Value]) -> Result<Execution<'_>, RuntimeError>`、`Vm::new_coroutine(Value) -> Result<HostHandle<Value>, VmError>`、`Vm::resume(Value, &[Value]) -> Result<Execution<'_>, RuntimeError>`，以及 `HostHandle<Value>::as_value(&Vm) -> Result<Value, VmError>`；後者須先驗證 VM 身分、root 與物件世代。`Vm::register_callback(&[Value], Rc<CallbackFn>) -> Result<HostHandle<Value>, VmError>` 登錄顯式 Lua 捕獲；`CallbackContext::capture` 讀取它們，`call`、`resume`、`yield_with` 建立動作。`CallbackResult` 為 `Return(Vec<Value>)`、`Throw(Value)`、`Call`、`Resume` 或 `Yield`；後三者帶 `CallbackContinuation::new(captures, callback)`，供原 `Execution` 完成動作後續接。顯式 `Value` 捕獲由 VM 驗證身分並追蹤 GC／配置；藏在任意 Rust closure 裡的宿主私有捕獲由宿主自行管理，不能冒充 VM root。回呼不取得第二個可變 VM 或 heap borrow；巢狀 basic pending 沿用 32 層上限、同一 `Execution` 的 fuel 與 LuaError／`Aborted` 邊界；不可 yield 的位置回結構化錯誤。這是 P13 局部介面契約與測試證據，不代表 P14 SDK、完整 gate 或 CI 已完成。
